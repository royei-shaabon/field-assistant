# אפיון MVP — עוזר תקלות לטכנאי, Yamaha NMAX

Oct 28, 2026 · @roei

## מטרה

ה-MVP מראה עוזר תקלות לקטנוע Yamaha NMAX. העוזר מוביל טכנאי צעד אחר צעד לפי מאגר ידע סגור: מדריך היצרן, ומעליו ידע שטח של מכונאי ותיק. הוא לא ממציא צעדים, וכשהצעד מסוכן הוא עוצר ומעביר לבכיר.

**למה NMAX:** מכשיר אחד, מוכר, זמין לצילום, עם מדריך רשמי וטבלת תקלות. בפגישה מציגים אותו כמחליף לציוד של הלקוח. המנגנון זהה (מאגר ידע, עץ בדיקות, עצירה, שימור ידע), ורק התוכן מתחלף.

**הסיכון שצריך לנהל:** מנהל שירות של מעליות או גנרטורים עלול להגיד "קטנוע זה לא הציוד שלנו". לכן בפגישה אומרים בפירוש: "זה הדגמה של מנגנון, והתוכן אצלכם יגיע מהטכנאים שלכם". בסוף שואלים איזו תקלה שלהם הייתה מתאימה לבדיקה ראשונה.

**מה ה-MVP מוכיח:**

- מאגר ידע מסודר מוביל אבחון בלי שהמודל ממציא.
- ידע של מכונאי ותיק מופיע בתשובה עם שם ומקור.
- צעד מסוכן נחסם בקוד, ולא רק בפרומפט.
- ותיק מוסיף ידע חדש תוך פחות מדקה.

**מה ה-MVP לא מוכיח:** חיסכון, FTFR, קיצור חפיפה. לא מציגים מספרים כאלה.

## היקף

ה-MVP מכסה דגם ושנתון אחד, ו-8 תקלות. מקבעים את הדגם לפי האופנוע שזמין לך לצילום.

**הערה על השם:** "NMAX 160" הוא שם שיווקי בחלק מהשווקים. בפועל מדובר במנוע של 155 סמ"ק, ובמדריכים הדגם מופיע לרוב כ-NMAX 155 או GPD155. לפני שמתחילים, מוודאים את קוד הדגם והשנתון מתוך הרישיון או ה-VIN, ומורידים את המדריך שמתאים בדיוק לקוד הזה.

## מקורות מידע

יש ארבעה מקורות, לפי סדר עדיפות. כל פריט במאגר חייב להצביע על אחד מהם. פריט בלי מקור לא נכנס.

| # | מקור | מה לוקחים ממנו | מאיפה | הערות |
| --- | --- | --- | --- | --- |
| 1 | **מדריך בעלים רשמי (Owner's Manual)** של הדגם והשנתון | טבלת פתרון תקלות, משמעות נוריות, תנאי הפעלה (מפתח חכם, עצירה-התנעה), לוח טיפולים, מפרט | אתר Yamaha של המדינה הרלוונטית. ב-Yamaha Europe צריך חשבון MyYamaha חינמי ([הסבר](https://whateverwheels.co.uk/info/yamaha-owners-manual.php)). אם אין, יבואן Yamaha בישראל | המקור הראשי. נכנס לתיקייה `sources/` מקומית, לא לריפו ציבורי |
| 2 | **מדריך שירות (Service Manual)** | טבלת קודי תקלה של ה-ECU, נהלי בדיקה למוסך | רק עותק חוקי: רכישה דרך היבואן או ממוסך מורשה שמשתמש בו | אופציונלי ל-MVP. בלי מדריך שירות לא נכנסים לקודי תקלה מספריים |
| 3 | **מכונאי ותיק** (מוסך Yamaha או מכונאי קטנועים) | מה בודקים קודם בפועל, טעויות של חדשים, מתי עוצרים | ראיון מוקלט של 60–90 דקות, לפי שאלון קבוע (בהמשך הסעיף) | זה המבדל של המוצר. כל טיפ נשמר עם שם ותאריך |
| 4 | **צילומים שלך** של לוח המחוונים | תמונות לזיהוי ולבדיקות קבלה | מצלמים בעצמך: מצב רגיל, כל נורית שאפשר להדליק באופן בטוח, וזוויות ותאורה שונות | לא מורידים תמונות מהאינטרנט |

**כללי איסוף:**

1. אתרי צד שלישי (כמו [ManualsLib](https://www.manualslib.com/n/nmax.html)) משמשים רק כדי לבדוק אילו מדריכים קיימים. התוכן עצמו נלקח מהמדריך הרשמי.
2. במדריכים כתוב שאסור להעתיק מהם. לכן לא מעתיקים פסקאות. כל צעד נכתב מחדש במילים שלך, בעברית קצרה, עם מספר עמוד.
3. כל רשומה מקבלת שדה `source` עם סוג המקור, המסמך ועמוד, או שם המכונאי ותאריך.
4. כשהמכונאי והמדריך סותרים זה את זה, שומרים את שניהם ומסמנים `conflict: true`. העוזר מציג קודם את המדריך ומוסיף לידו את הטיפ.

**שאלון למכונאי (חוזר על עצמו בכל תקלה):**

1. איך זה נראה כשמגיעים? מה הרוכב מספר?
2. מה הסיבה הכי נפוצה בפועל, ומה השנייה?
3. מה בודקים ראשון, ולמה בסדר הזה?
4. איך יודעים שהבדיקה עברה ואיך יודעים שנכשלה?
5. איפה טכנאי חדש טועה?
6. מתי עוצרים וקוראים לבכיר?
7. מה במדריך לא מספיק או לא נכון?

## מבנה מאגר הידע

המאגר הוא עץ החלטות סגור, לא טקסט חופשי. כל תקלה היא קובץ YAML אחד, ובו צעדי בדיקה ממוספרים. לכל צעד יש מקור, ולכל תוצאה יש מעבר מוגדר. המודל לא כותב צעדים. הוא רק מזהה תקלה ומפרש תשובות.

**תיקיות:**

```
knowledge/
  device.yaml              # דגם, שנתון, קוד דגם, גרסת מדריך
  sources.yaml             # רשימת מקורות: id, סוג, שם, תאריך
  symptoms/
    no-crank.yaml          # תקלה = קובץ
    crank-no-start.yaml
    engine-light.yaml
    ...
  tips/                    # טיפים שנוספו מהאפליקציה, ממתינים לאישור
  schema/
    symptom.schema.json
    tip.schema.json
sources/                   # PDF-ים מקומיים, ב-.gitignore
```

**סכמת תקלה (דוגמה מקוצרת):**

```
id: no-crank
title: המנוע לא מתניע, אין סיבוב מתנע
visual_cues: ["לוח דולק", "אין צליל מתנע"]
steps:
  - id: s1
    check: האם רגלית הצד מקופלת?
    how: ...
    source: { type: manual, ref: owners-2024, page: 0 }
    hazard: false
    on_pass: s2
    on_fail: { resolve: "לקפל רגלית ולנסות שוב" }
  - id: s2
    check: האם ידית בלם לחוצה בזמן ההתנעה?
    source: { type: manual, ref: owners-2024, page: 0 }
    tip: { author: "<שם המכונאי>", text: "..." }
    on_pass: s3
    on_fail: { resolve: "..." }
  - id: s5
    check: בדיקת מתח מצבר
    hazard: false
    on_fail: { escalate: "חשד לתקלת מערכת הטעינה" }
escalate_after_steps: 6
```

**כללים שהוולידציה אוכפת** (`npm run kb:validate`, רץ גם ב-CI):

- כל קובץ עובר את הסכמה.
- לכל צעד יש `source` שקיים ב-`sources.yaml`.
- כל `on_pass` ו-`on_fail` מובילים לצעד קיים, ל-`resolve` או ל-`escalate`. אין צעדים יתומים, ואין לולאות.
- צעד עם `hazard: true` חייב להוביל ל-`escalate`.
- `visual_cues` לא ריק, כי סקיל הזיהוי נשען עליו.

**טיפ חדש מהאפליקציה** לא נכנס ישר לעץ. הוא נשמר ב-`tips/` במצב `pending`. ותיק מאשר ומשייך אותו לצעד, ואז הוא מופיע. כך שומרים על מאגר נקי.

## סקילים

במוצר יש 4 סקילים, וכל אחד הוא קריאה אחת למודל עם קלט מוגדר ופלט JSON שעובר ולידציה. המודל לא בוחר איזה סקיל להפעיל. את זה מחליט הקוד (בסעיף הבא).

| סקיל | מתי רץ | קלט | פלט (JSON) | אסור לו |
| --- | --- | --- | --- | --- |
| `identify` | תחילת שיחה | תמונה ו/או טקסט, ורשימת ה-`id` וה-`visual_cues` של כל התקלות | `symptom_id` מתוך הרשימה או `unknown`, `confidence` (high/medium/low), `reason` קצר | להחזיר תקלה שלא ברשימה. לתת עצה |
| `interpret` | אחרי כל תשובה של הטכנאי | הצעד הנוכחי (`check`, `how`) והטקסט שהטכנאי כתב | `outcome`: pass / fail / unclear / danger, ו-`note` | להחליט מה הצעד הבא. לתת הוראה |
| `summarize` | בהסלמה | מסלול הצעדים והתוצאות | סיכום של 3–5 שורות לבכיר | להוסיף השערות שלא נבדקו |
| `structure_tip` | ותיק שומר הקלטה | תמלול ורשימת התקלות והצעדים | טיוטת טיפ: `symptom_id`, `step_id` מוצע, `text` | לשמור. הוותיק מאשר |

**איך כל סקיל בנוי בריפו:**

```
skills/identify/
  prompt.md        # הוראות קצרות, בלי ידע מקצועי בתוכן
  schema.json      # פלט מותר
  examples.yaml    # 5–10 דוגמאות קלט/פלט
  identify.test.ts # בדיקות על תמונות וטקסטים קבועים
```

**כללים משותפים לכל הסקילים:**

- הפלט עובר ולידציה מול `schema.json`. אם הוא לא תקין, יש ניסיון חוזר אחד, ואחריו `unclear` או `unknown`. לא ממשיכים עם פלט שבור.
- `temperature: 0`.
- הטקסט שהטכנאי רואה מגיע מהמאגר (`check`, `how`, `tip`), ולא מהמודל. המודל רק מסווג.
- שום סקיל לא מקבל כלים (tool use), גישה לרשת או כתיבה למאגר.

## גבולות האייג'נט

אין אייג'נט חופשי. מכונת מצבים בקוד (`lib/orchestrator.ts`) מנהלת את השיחה, והמודל מופעל רק בשני צמתים: זיהוי התקלה ופירוש תשובת הטכנאי. כל השאר קבוע.

&#91;embedded content: מכונת המצבים · המודל בשני צמתים בלבד\]

הטכנאי רואה רק טקסט שיש לו מקור במאגר, וכל צעד עובר בדיקת בטיחות לפני שהוא מוצג.

**מה המודל לא יכול לעשות:** לבחור צעד הבא, לכתוב הוראה, לדלג על בדיקת הבטיחות, לפנות לרשת, או לשנות את המאגר.

**מצבים בקוד:** `IDENTIFYING` ואחריו `STEP`, ואחריו `AWAITING_ANSWER`, ומשם חזרה ל-`STEP` או ל-`RESOLVED` או ל-`ESCALATED`. כל מעבר שלא מוגדר בעץ מוביל ל-`ESCALATED`.

## בטיחות

כל כללי הבטיחות נאכפים בקוד, בקובץ `lib/safety.ts`. הפרומפט לא אחראי עליהם.

- צעד עם `hazard: true` לא מוצג כהוראה. במקומו מופיע באנר עצירה וכפתור "העבר לבכיר".
- נושאים שמסומנים מראש כ-hazard: מערכת הבלמים וה-ABS, מערכת הדלק, פתיחת מכסה נוזל קירור כשהמנוע חם, וכל עבודה במנוע שפועל.
- אם `interpret` מחזיר `danger` (עשן, ריח דלק, ריח שריפה, נוזל דולף, פגיעה), עוברים מיד להסלמה.
- הסלמה אוטומטית אחרי `escalate_after_steps`, או אחרי שתי תשובות `unclear` ברצף.
- אם `identify` מחזיר `low` או `unknown`, מבקשים תמונה נוספת. בפעם השנייה, הסלמה.
- בתחתית כל מסך: "דמו על ידע לדוגמה. לא הוראות עבודה מאושרות."

## מסכים

יש 4 מסכים, בעברית RTL, מתוכננים לטלפון. מעבר בין טכנאי לוותיק נעשה דרך מתג בראש המסך.

1. **בית (טכנאי):** "צלם את לוח המחוונים" או "תאר תקלה", ומתחת 3 שיחות אחרונות.
2. **שיחת תקלה (טכנאי):** כרטיס זיהוי עם שם התקלה ורמת ביטחון. אחריו הצעד הנוכחי עם תג מקור ("מדריך בעלים, עמ' X" או "טיפ של <שם>"). כפתורים: "עבר", "נכשל", "לא הבנתי", וגם שדה טקסט חופשי. מעל הכול סרגל התקדמות (צעד 2 מתוך 5).
3. **הקלטת ידע (ותיק):** בוחרים תקלה, מקליטים עד 60 שניות, רואים את התמלול ואת הטיוטה המובנית, ומאשרים או עורכים.
4. **מאגר (ותיק):** עץ הצעדים של כל תקלה עם המקורות, טיפים שממתינים לאישור, ומונה שימוש לכל טיפ.

## ארכיטקטורה, ריפו ו-Claude Code

כל המערכת היא פרויקט Next.js אחד. ההחלטות נמצאות בקוד (`orchestrator`), המודל רק מסווג, והמאגר הוא קבצי YAML בריפו.

| רכיב | בחירה |
| --- | --- |
| אפליקציה ושרת | Next.js + TypeScript + Tailwind, `dir="rtl"`, פריסה ב-Vercel |
| מודל | Claude API, `claude-sonnet-5-5`, עם תמונה ופלט JSON |
| מאגר ידע | YAML בריפו, נטען בזמן build |
| שיחות וטיפים | Supabase (Postgres + Storage) |
| תמלול | Whisper API או Web Speech. נבדק מול עברית טכנית |

**מבנה ריפו:**

```
CLAUDE.md                 # כללי עבודה ל-Claude Code
.claude/skills/           # סקילים לפיתוח (למטה)
knowledge/                # המאגר (סעיף מבנה מאגר הידע)
skills/                   # 4 סקילי המוצר
lib/orchestrator.ts       # מכונת המצבים
lib/safety.ts             # חסימות
lib/kb.ts                 # טעינה ושאילתות על המאגר
app/                      # מסכים ו-API routes
scripts/kb-validate.ts
tests/fixtures/photos/    # תמונות בדיקה שצילמת
```

**`CLAUDE.md` — כללים שהאייג'נט בפיתוח חייב לכבד:**

- לא משנים את `knowledge/` בלי `source` ובלי להריץ `kb:validate`.
- לא משנים את `lib/safety.ts` בלי להוסיף בדיקה.
- לא כותבים ידע מקצועי בפרומפטים של הסקילים. ידע יושב רק במאגר.
- לא מוסיפים כלים, גישה לרשת או כתיבה למאגר לסקילי המוצר.
- כל שלב בנייה נגמר כשהבדיקות שלו עוברות.

**סקילים לפיתוח ב-Claude Code (`.claude/skills/`):**

| סקיל | מה עושה | בדיקת סיום |

## תסריט הדמו

הדמו נמשך 7 דקות, בסוף פגישה של 45 דקות. לפניו 30 דקות של ראיון גילוי ניטרלי, לפי מסמך המחקר.

1. **פתיחה (30 שניות):** "זה הדגמה של מנגנון על קטנוע. אצלכם במקומו יהיה הציוד שלכם והטכנאים שלכם."
2. **תקלה פשוטה (1.5 דקות):** "המפתח החכם לא מזוהה". העוזר מזהה, נותן צעד מהמדריך, הטכנאי עונה "עבר", העוזר נותן צעד הבא, והתקלה נפתרת.
3. **ידע שטח (1.5 דקות):** "לא מתניע". הצעד הראשון מתויג "טיפ של <מכונאי>", וזה צעד שלא מופיע במדריך. נקודה להדגיש: זה מה שמבדיל מ-ChatGPT.
4. **עצירה (1 דקה):** "נורית ABS". מגיעים לצעד שמסומן hazard, מופיע באנר עצירה, ומיד אחריו סיכום מוכן לבכיר.
5. **שימור ידע (1.5 דקות):** עוברים לוותיק, מקליטים טיפ, מאשרים, חוזרים לתקלה, והטיפ מופיע.
6. **שאלות:** "איזו תקלה אצלכם הייתם רוצים לבדוק ככה ראשונה?", "מי מחזיק היום את הידע הזה?", "איך הייתם מודדים שזה עובד?", "מה היה צריך להיות נכון כדי לנסות עם טכנאי אחד?"

**לא אומרים:** מחיר, חיסכון, "מחליף ותיקים". **גיבוי:** תמונות מוכנות בטלפון, ווידאו מוקלט של כל התסריט.
